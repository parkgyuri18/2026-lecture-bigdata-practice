# Week 6 — Observations

## Task 1 — A-Priori와 연관 규칙
동일한 기본 데이터(seed 246, 바구니 20,000개, support 50)의 앞선 검증에서 최고 confidence 규칙은 1468 → 0으로 0.838710이며, 반대 방향 0 → 1468은 0.003976이었다. 따라서 항목 1468로부터 항목 0을 예측하는 방향이 유용하며 confidence는 대칭이 아니다.
이 규칙의 lift는 1.282431로, 항목 0의 높은 기본 출현율을 고려하면 관계의 강도는 제한적이며 높은 confidence만으로 강한 연관성이나 인과관계를 주장할 수 없다.
2,000개 항목의 전체 가능한 쌍은 1,999,000개이고, 앞선 pass 1 검증에서 살아남은 1,849개 항목의 가능한 쌍은 1,708,476개였다. 이번 bench.txt에서 실제로 유지한 관찰 쌍 카운터는 820,259개로, 가능한 모든 쌍을 미리 저장한 것은 아니다.

## Task 2 — Support를 낮추었을 때의 변화
첨부한 explosion.json에서는 support 400부터 1까지 9개 값을 실행했으며, support 1도 5.155초와 최대 추적 메모리 334.153MB로 완료됐다. 자원 고갈이나 중단 지점은 관찰되지 않았고, 카운터는 support 25부터 893,456개로 포화되어 A2가 기대한 실패 지점에는 도달하지 않았다.
400 → 200 → 100 → 50 구간에서 카운터는 각각 5.54배, 4.67배, 3.00배 증가했지만 빈발 쌍은 3.12배, 2.89배, 2.85배 증가했다. Support 50에서는 답 6,397개를 찾기 위해 820,259개의 카운터가 필요했고, support 25 이하에서는 카운터가 고정된 채 답만 늘어나 support 1에서 두 수가 같아졌다.
측정 환경은 Intel Core i5-1240P, RAM 약 15.64GiB, Windows 11, Python 3.14.7이며 시작 시 사용 가능한 RAM은 약 1.81GiB였다. MB는 10^6 bytes이고 tracemalloc 값은 전체 프로세스 메모리가 아니다. 다른 실행 앱은 첨부 자료로 확인되지 않으며 JSON의 execution_context 문구만으로 실제 실행 앱을 확정하지 않았다.

## Task 3 — PCY의 카운터 감소와 메모리 비용
이번 bench.txt에서는 기준과 PCY가 모두 빈발 쌍 6,397개를 찾았고 missing 0, extra 0이었다. 최대 쌍 카운터는 820,259개에서 13,290개로 98.38% 감소해 strong 기준을 충족했지만 실행 시간은 1.29초에서 2.55초로 늘어났으므로 개선점은 속도가 아니라 카운터 수이다.
제공된 구현은 충돌을 줄이기 위해 버킷 1,000,003개를 사용하며 64비트 배열의 데이터 영역은 8,000,024 bytes, 비트맵은 125,001 bytes이다. 변환 중에는 둘이 함께 존재하고 pass 2 전에 배열을 해제한다. 이번 bench.txt만으로 전체 메모리 절감량이나 교차점을 직접 측정했다고 말할 수는 없다.
별도의 앞선 Python 3.12.14 보조 실험에서는 바구니 5,000개에서 PCY/기준이 8.366/6.491MB, 20,000개에서 8.493/102.288MB여서 교차점을 두 크기 사이로 좁혔고, 작은 버킷 10,007개에서는 충돌 때문에 카운터가 820,259개로 늘었다. 이는 이번 Python 3.14.7 실행의 측정값이 아닌 참고 실험이며, 교차점은 support·분포·버킷 수·자료구조에 따라 달라진다.

## Task 4 — SON과 청크 수 비교
이번 task4.txt에서 청크 수 4/8/16에 따른 후보 수는 9,876/14,201/24,418개였지만 최종 빈발 쌍은 모두 6,397개였고, 누락·추가가 없으며 각 쌍의 support도 기준과 일치했다. 청크별 국소 빈발 쌍을 합치므로 후보는 실제 답보다 많을 수 있고, pass 2가 전체 데이터에서 거짓 양성을 제거한다.
전체 바구니 수를 N, 청크 크기를 n_i, 전체 임계값을 s라 하면 청크 임계값은 ceil(s·n_i/N)이다. 전역 빈발 쌍이 모든 청크에서 탈락했다고 가정하면 정수인 각 청크 출현 횟수 c_i는 c_i < s·n_i/N을 만족하므로 합계가 s보다 작아져 전역 빈발이라는 가정과 모순된다. 따라서 누락이 없어야 한다.
SON 실행 시간은 4/8/16개 청크에서 각각 5.49/2.95/2.86초였고, 같은 실행의 기준은 1.52/1.24/1.20초였다. 이는 단일 측정이며 후보가 늘어도 실행 시간이 반드시 늘지는 않았고, 청크별 A-Priori 비용과 실행 변동도 영향을 줄 수 있다. 이번 데이터에서는 기준보다 느렸지만 SON은 청크별 독립 처리를 통해 분산 실행에 적용할 수 있으며, 이번 기록은 단일 프로세스 실행으로 Spark의 성능을 측정한 것은 아니다.
