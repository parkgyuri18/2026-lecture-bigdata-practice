# Task 2 — Support 임계값에 따른 후보 쌍 증가 실험

## 실행 환경과 측정 방법 (A6)

- CPU: 12th Gen Intel(R) Core(TM) i5-1240P
- RAM: 16,788,488,192 bytes (약 15.64 GiB), 측정 시작 시 사용 가능한 RAM 약 1.81 GiB
- 운영체제: Windows-11-10.0.26200-SP0
- Python: 3.14.7
- 실행 중인 다른 앱은 첨부 자료로 확인되지 않는다. JSON의 execution_context는 고정된 설명 문구일 수 있으므로 이를 근거로 실제 실행 앱이나 실행 경로를 확정하지 않았다.
- 데이터: 기본 bench.build()의 바구니 20,000개, 항목 2,000개, seed 246.
- 출처: 함께 제공한 explosion.json의 9개 측정 기록. 각 행은 1회 실행 결과이며 평균값이 아니다.

메모리는 tracemalloc으로 알고리즘 실행 중 추적한 최대 할당량이다. 결과 딕셔너리는 포함하지만, 추적 시작 전에 만든 입력 바구니와 전체 프로세스 메모리는 포함하지 않는다. MB는 1,000,000 bytes 기준이다. 메모리 추적 자체의 실행 시간 부담도 포함된다.

## 중단 지점과 자원 고갈 여부 (A2)

최소 양의 정수 임계값인 support 1까지 실행이 완료됐다. 이때 실행 시간은 5.155초, 최대 추적 메모리는 334.153MB였다. 이번 측정에서는 메모리 부족이나 실행 중단을 관찰하지 않았으므로, 버티지 못한 support나 먼저 고갈된 자원이 있다고 주장할 수 없다.

카운터 수는 support 25부터 1까지 893,456개로 같았다. 이 데이터에서는 관찰된 모든 쌍이 이미 후보에 들어간 상태이므로 임계값을 더 낮추어도 새로운 관찰 쌍은 생기지 않는다. 과제 A2가 기대하는 자원 고갈 지점에는 도달하지 않았다는 한계를 명시한다.

## 카운터 증가율 (A4)

Support를 400→200→100→50으로 절반씩 낮추자 카운터 수는 각각 5.54배, 4.67배, 3.00배 증가했다. 이 구간에서는 단순한 두 배 증가보다 빠르게 커졌다. 그러나 50→25에서는 1.09배 증가했고, 그 아래에서는 포화되어 증가하지 않았다. 따라서 모든 구간에서 같은 증가율을 가진다고 해석할 수 없다.

## 빈발 쌍과 카운터 수의 차이 (A5)

400→200→100→50 구간의 빈발 쌍 수는 각각 3.12배, 2.89배, 2.85배 증가해 카운터보다 느리게 증가했다. Support 50에서는 답 6,397개를 찾기 위해 820,259개의 카운터를 유지했으며, 답 하나당 약 128.22개의 카운터가 필요했다. 최종 결과에서 버려질 쌍도 세어야 한다는 점이 메모리 부담의 핵심이다.

반면 support 25 이하에서는 카운터가 고정된 상태로 빈발 쌍 수가 계속 증가했다. Support 1에서는 모든 관찰 쌍이 답이 되어 두 수가 같아졌다. 이때는 반환하는 결과 딕셔너리도 커지므로 카운터 수가 같아도 최대 메모리가 증가할 수 있다. 따라서 빈발 쌍 수가 항상 카운터보다 느리게 증가한다는 설명은 전체 구간에 적용되지 않는다.

## 재실행 명령

```bash
python3 task2_explosion.py --supports 400,200,100,50,25,12,6,3,1
```

이 명령은 기존 JSON에 측정 기록을 추가한다. 다른 환경에서 새로 측정할 경우 기존 기록을 별도 보관하고 새 결과에 맞춰 실행 환경, 표, 해석을 함께 갱신해야 한다.
